## 3. Algorithm overview and implementation decisions

### LCS
`dp[i][j]` stores the LCS length for the first `i` characters of the first string and the first `j` characters of the second string. If the last characters match, the value is `dp[i-1][j-1] + 1`; otherwise it is the maximum of the cell above and the cell to the left. The first row and column are zero.

### Edit Distance
`dp[i][j]` stores the minimum edits needed to convert prefixes of lengths `i` and `j`. The first row and column represent converting to or from an empty string. Each cell takes the minimum of deletion, insertion, and substitution/match.

### Naive matching
Every possible starting position is checked character by character. It is the baseline implementation.

### KMP
KMP builds an LPS (Longest Proper Prefix which is also Suffix) table for the pattern. After a mismatch, the LPS value shifts the pattern without rechecking text characters already known to match.

### Rabin–Karp
The algorithm compares rolling hashes for each text window. A hash match is verified character by character, so collisions cannot create false reported matches. The implementation uses base 256 and modulus 1,000,000,007.

### Kasai
The input suffix array is assumed to be supplied. The algorithm builds inverse ranks and computes `lcp[i]`, the common-prefix length of suffix `suffixArray[i]` and the previous suffix in lexicographic order. `lcp[0]` is zero. The carried common-prefix length is reduced by one after each step.

### Assumptions
- Strings are Java `String` values and comparisons use UTF-16 `char` units.
- An empty pattern matches at every boundary: indices `0` through `text.length()`.
- A pattern longer than the text has no matches.
- Kasai receives a valid suffix array containing every suffix start index exactly once.
- The benchmark alphabet is lowercase English letters: `abcdefghijklmnopqrstuvwxyz`.
- Random generation uses seed `42`.

## 4. Complexity analysis

Let `n` and `m` be the two string lengths for DP; for matching, let `n` be text length and `m` pattern length.

| Algorithm | Main operation / recurrence | Best time | Worst time | Auxiliary space |
|---|---|---:|---:|---:|
| LCS | Match: `1 + dp[i-1][j-1]`; mismatch: `max(dp[i-1][j], dp[i][j-1])` | O(nm) | O(nm) | O(nm) |
| Edit Distance | `min(delete, insert, substitute)` | O(nm) | O(nm) | O(nm) |
| Naive | Compare pattern at each text position | O(n) for fixed `m` / immediate mismatches | O(nm) | O(1) excluding output |
| KMP | LPS preprocessing, then failure-function transitions | O(n + m) | O(n + m) | O(m) |
| Rabin–Karp | Rolling hash for each window, verify hash hits | O(n + m) expected | O(nm) | O(1) excluding output |
| Kasai | Inverse rank + carried LCP comparison | O(n) | O(n) | O(n) |

For Naive matching, a full scan with an immediate mismatch per position is linear; repeated long partial matches can cause `O(nm)`. KMP never moves the text index backward. Rabin–Karp is expected linear when hash collisions are uncommon, but verification at many hash-hit windows can make the worst case `O(nm)`. Kasai is linear because the carried common-prefix length decreases by at most one per outer iteration and increases only a total linear number of times.

## 8. Discussion

The DP algorithms use a two-dimensional table and therefore scale quadratically in the two input lengths in both time and memory. KMP has a linear bound and avoids repeated comparisons by using its LPS table. Naive matching is simpler but can repeat work. Rabin–Karp can be efficient with few hash hits, while collision verification explains its worst-case bound. Kasai computes all adjacent-suffix LCP values in linear time after the suffix array is supplied.

Measured times can differ from theoretical growth because of JVM warm-up, garbage collection, CPU frequency, memory allocation, and input characteristics. The theoretical bounds describe growth as input size increases; the benchmark records actual execution on one machine.

## 9. Conclusion

The project demonstrates different trade-offs. LCS and Edit Distance solve optimization problems with dynamic programming tables. Naive matching is straightforward but may be slow on repetitive inputs. KMP provides predictable linear-time matching. Rabin–Karp uses rolling hashes and verifies possible collisions. Kasai efficiently constructs the LCP array when a suffix array is already available.
